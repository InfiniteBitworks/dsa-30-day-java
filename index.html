What a month actually buys you

Thirty days at one to three hours is somewhere between 30 and 90 hours of work. That is not enough to master this material, and anyone selling you that is lying. Here is the real trade, for someone starting from scratch.

At the end you should be able to look at a new problem and recognise which of a dozen or so patterns it's built from, write the standard structures — stack, queue, tree, graph — without hesitating over the Java API, and solve the majority of easy and a fair share of medium problems on your own. That's a genuinely different skill level from where you're starting. Deep fluency, hard problems, and contest-level speed are a six-to-twelve month project this month becomes the foundation for.

The single thing that decides your outcome is not the plan. It is whether you re-solve the problems you failed. Most people skip that part, which is why most people plateau — and it matters even more starting from zero, because the first pass through a new pattern rarely sticks.

How to run a session

1 hour

The floor

15 minutes learning the day's concept, then two problems. Skip the theory rabbit holes — you learn the structure by using it.

2 hours

The target

Everything above, plus two more problems and one re-solve of something from three days ago, from scratch, no notes.

3 hours

The full session

Everything above, plus read two editorials for problems you already solved to find a better approach, and hand-write the day's template into your notes.

Five rules that matter more than the schedule

  • The 25-minute rule. Stuck for 25 minutes with no new idea? Read the solution, understand it, close the tab, and rewrite it from an empty file. Staring longer teaches you nothing; it just hurts.
  • Type every line. Never copy-paste a solution, not even your own. Your hands need the reps as much as your head does.
  • Keep a failed list. One text file. Every problem you couldn't finish alone goes in it, with the date. Re-solve each one after 3 days and again after 10. Day 30 exists for this list.
  • Say the approach out loud before coding. Brute force first, then its complexity, then the improvement. This is how you catch a flawed idea before you've spent twenty minutes coding it — silent coding hides gaps in your own thinking.
  • Miss a day, don't miss two. If you fall behind, drop the optional problems rather than skipping days. Continuity beats volume.

The Java you want in your fingers

Learn these cold in week one. Fumbling API calls is what makes an easy problem feel hard — the syntax should be invisible so all your thinking goes toward the actual logic.

// counting
Map<Character,Integer> freq = new HashMap<>();
freq.merge(c, 1, Integer::sum);
freq.getOrDefault(c, 0);

// grouping
Map<String,List<String>> g = new HashMap<>();
g.computeIfAbsent(key, k -> new ArrayList<>()).add(word);

// stack AND queue — use ArrayDeque, never Stack or LinkedList
Deque<Integer> stack = new ArrayDeque<>();   // push / pop / peek
Deque<Integer> queue = new ArrayDeque<>();   // offerLast / pollFirst

// heap
PriorityQueue<int[]> pq = new PriorityQueue<>((a,b) -> a[1] - b[1]); // min by a[1]

// sorting 2D arrays — Integer.compare avoids overflow, subtraction doesn't
Arrays.sort(intervals, (a,b) -> Integer.compare(a[0], b[0]));

// strings
StringBuilder sb = new StringBuilder();   // never use += inside a loop
char[] cs = s.toCharArray();
int[] count = new int[26];                // faster than a map for a–z

// the two lines people get wrong
int mid = lo + (hi - lo) / 2;             // not (lo + hi) / 2
if (a.equals(b))                          // not a == b, for Integer above 127
